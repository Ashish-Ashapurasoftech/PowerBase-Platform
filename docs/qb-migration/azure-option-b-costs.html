2. Recommended for client performance: dedicated database capacity

The worker writes into the live PowerBase SQL. The new resource group keeps the migration's own services apart from live, but those writes still land on the live database. For large apps (20–40 million records over about 15 days), a separate SQL elastic pool for the migrating tenants means clients' databases never share CPU, memory or disk activity with the load.

3. Considered and not needed

  • Service Bus Premium (≈ $677/month): built for very high message rates; ours is about 2,000 messages.
  • Second worker VM: QuickBase's API limit (about 10 requests per second per token) is the bottleneck, not the VM. One D4s v5 runs 8–10 parallel workers. A second VM helps only when several apps run in parallel with separate tokens.
  • Azure Bastion (≈ $140/month): SSH is limited to the office IP instead.

4. How live clients are protected during the run

  • The worker runs on its own VM. The live API, App Service and live Service Bus carry none of the migration's work.
  • Parallelism is capped and raised step by step (2 → 4 → 8 workers) while database CPU is watched. Big apps can run off-peak.
  • The worker can be stopped at any moment and resumed later without duplicates. This is tested: a hard kill mid-run, then a resume, gave the exact same data.
  • Each app is loaded into a new, empty PowerBase app; existing apps and records are never written to.
  • Every app is checked before go-live: record counts, record IDs, field-by-field comparison and links between tables.

6. Needed before deployment

  1. Where the live PowerBase SQL is: server name and subscription. The dev@yslworkflow.com account currently sees only the UAT server. The new resources go in the same region as live SQL.
  2. Firewall rule on the live SQL server for the worker VM's fixed IP, added by the server's owner.
  3. Search capacity check: 20–40 million records will be added to the Azure AI Search index. Confirm the current tier can hold them before the large apps.
  4. Decision on section 2 (dedicated pool or throttled writes) before the first large app. Not needed for the small-app pilot.
